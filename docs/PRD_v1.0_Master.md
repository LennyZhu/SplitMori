## 1. 产品定位与成功标准

### 1.1 已冻结产品方向

- 正式名称 **SplitMori**；继续采用与 OrderMori 相近的暖白、深炭黑、专业极简风。
- 主要场景：香港的 2–12 人聚餐、饭局；次要场景：旅行、活动、多笔消费。
- 目标平台：iOS / iPhone 优先；繁體中文（香港）+ English；支持系统语言与手动语言偏好。
- Local-First，1.0 不需要账号、云同步或后端，参与者不必安装 App。
- Free 可以完成常用分账；Pro 为**非消耗型、一次买断**，不做订阅或广告。

### 1.2 要解决的问题

1. **立即知道每个人最终承担多少**，即使不知道是谁先付款。
2. **请客可解释**：老板出大头而剩余他人 AA，并明确老板是否参与剩余金额。
3. **各自消费可解释**：每个人的个人消费、公共消费、服务费、优惠都有清楚依据。
4. **多人实际垫付可结算**：同一活动不同账单的付款人可能不同，计算谁向谁还钱。
5. **已付钱后账单发生变化也不乱账**：商家真实退款、录入更正、成员还款是不同事实。
6. **一张图发到群聊**：由一人完成，不强迫其他人注册或安装。

### 1.3 产品验收目标（待验证，不是性能承诺）

- 最普通的总额 + 人数 AA，目标在 30 秒内完成；真实可用性测试后再判定。
- Free 不因已有活动而阻止临时快速试算，也不因笔数过多而阻止当前活动记账。
- 全部合法数据必须满足账务守恒；分享值和页面显示值一致。
- 离线可使用计算、正式账本、还款、退款记录（在可编辑活动中）、基础 PNG 分享和数据备份。

## 3. 信息架构、路由和主流程

```text
S00 首次启动（直接进入体验）
  └─ S01 首页
       ├─ S02 快速分账 → S03 计算说明 → S04 结果 → S11 分享预览
       │                                 └─ 保存快速记录 / 加入活动
       ├─ S05 活动列表 → S06 新建/编辑活动 → S07 活动详情
       │                                       ├─ S08 新增/编辑费用 → 商家退款
       │                                       ├─ S09 结算 → S10 记录/更正还款
       │                                       └─ 完成活动 / 重新开启
       └─ S13 设置 → S12 Pro / 备份 / 语言 / 隐私 / 支持
```

### 3.1 快速试算 → 结果（不一定入账）

- 用户只输入总金额 + 人数，允许先用 `成員 1、成員 2` 等临时称谓直接得出份额。
- **快速试算可以不填实际付款人**：此时只显示每人应承担，不提供虚构的转账路线。
- 可以免费直接分享 PNG；保存为快速历史不等于产生正式费用；单纯试算永远不占 Free 活动配额。
- `加入活動` 是明确用户操作：确认选定活动/新建活动、成员 ID 映射、币种、付款人并进行**一次性的事务提交**；拒绝重复转换同一条试算。

### 3.2 正式活动账本

- 以活动为单位共享币种和成员表；每笔费用自带参与者、分账模式及付款事实。
- **正式入账必须指定对商家付款人**，且对商家付款合计 = 原始账单实付额；Free 同一笔只允许一名付款人。
- 已完成活动也能展示 `已完成 · 未結清` 和添加真实成员间还款；重开之后才能改费用/录商家退款。
- 结算建议随财务事件变化重新计算，**推荐路线是派生内容，不能充当已付款的证据**。

### 3.3 主要成功路径

| 路径 | 入口 | 用户动作 | 终态 |
|---|---|---|---|
| Q1 普通 AA | S01 | 总额→人数→结果 | 获得承担金额，直接分享 |
| Q2 老板请客 | S02 | 选老板→承担额→剩余均分规则 | 每人承担额清晰，实际付款人可选 |
| Q3 各自消费 | S02 | 每人总额→共享额→参与者→服务费/优惠 | 解释每人的构成 |
| Q4 多笔活动 | S05 | 新建活动→N 笔费用→结算→记录还款 | 每笔允许不同付款者 |
| Q5 完成后还款 | S05 | 找到已完成活动→结算→确认真实还款 | 状态保持已完成、余额更新 |
| Q6 商家退款 | S07 | 进行中活动某笔费用→记录真实退款→预览 | 退款收款人及分摊责任更新 |
| Q7 Pro | 触发高级能力 | 功能说明→实际商店价→购买/取消 | 权益更新或原草稿不变 |

## 4. 完整页面规格（S00–S13）

以下逐屏部分以 v0.6 设计为基底；页面结构是**建议的实施规格**，用户尚未逐屏最终视觉验收。业务权限与金额约束属于前述冻结要求。

统一描述：**进入条件 → 核心组成 → 默认动作 → 关键状态 → 收费边界**。

### S00 — 首次使用

- **进入**：新安装首次启动。
- **显示**：简洁品牌字标、一行价值陈述、`開始分帳`；无需创建用户资料或强制教程。
- **默认**：App 语言跟随 iOS（繁体中文香港优先匹配 zh-HK，其他语言回退 English 或按将来确认的策略）；币种初始建议 HKD，用户可选其他币种。
- **状态**：没有相册、联系人、通知的预先权限要求；可直接进入 S02。
- **收费**：不得首次启动自动弹 Pro 购买页。

### S01 — 首頁

- **页头**：品牌标识、设置入口、可选小字 `分帳，簡單就好。`
- **主操作**：全宽深色 `開始分帳`；次入口 `建立活動`。
- **进行中活动区**：显示活动名、笔数、当前账面总额、是否有未结清款项；点击进入 S07。
- **最近区**：手动保存的快速计算与已完成活动；没有记录时采用文字空状态而非营销图。
- **Free 活动名额**：已有进行中活动时仍允许无限快速试算；`建立活動` 时检查并出现 M02，不应在首页禁用按钮且无解释。
- **空态（zh-HK）**：`還沒有分帳記錄。輸入金額，就可以開始。`

### S02 — 快速分帳主編輯

**屏幕顺序**：
1. `實際帳單總額` 大金额输入、币种选择。
2. `分帳方式` 四选一：平均、请客、各自消费、自定义（Pro）。
3. `參與成員` 默认两位可增减的本地占位名称；允许直接用人数迅速均分，查看结果前可用临时成员代号。
4. 仅显示对应模式的输入区：
   - 平均：参与人勾选。
   - 请客：请客者、固定金额或单人承担百分比、是否参与剩余分摊；Free 一位、Pro 多位。
   - 各自消费：Free 每人消费总金额、公共消费总金额及参与人；Pro 可转入逐项消费子流程。
   - 自定义（Pro）：固定金额、每人百分比或份数。
5. `費用明細（選填）`：默认使用已含所有费用的总金额；展开后才输入小计、实际服务费或 10% 快捷、固定优惠。**切换必须确认该金额是含服务费的最终价还是小计**，禁止二次加服务费。
6. `誰先付款？（選填）`：可以跳过试算；Free 单位付款人，Pro 可添加多位对商家付款人。
7. 底部固定 `查看結果`，点击前预校验金额、参与人、总额守恒。

**操作**：切换模式保留金额/成员但不把旧模式的专属参数隐式应用；必要时展示“切换后哪些字段不再使用”。编辑中断保存草稿。

**错误**：未选参与人、请客承诺超账单、消费明细总额对不上、服务费重复加入、百分比不等于 100%、负数/超精度输入，在字段附近说明。

**Pro**：点高级能力时**立即解释**，先保留草稿再打开 Pro 页；购买取消返回原位置。不能等用户填完一大段高级字段才突然要求购买。

### S03 — 分攤明細（结果解释 Sheet）

- 每人展示：原消费或均分基准、请客承诺/剩余 AA、分配的服务费、减免的优惠、最终应承担。
- 可查看“为什么多了 0.01”的余数解释；历史费用按保存时的舍入顺序展示，不因改名变动。
- 显示总额守恒校验；不允许在解释页偷偷修改计算结果。
- **不收费**：Free 也必须能核对自己当前模式的计算依据。

### S04 — 快速結算結果

- 上部大字显示 `每人應承擔`；每人金额清单。
- 若已经指定实际商家付款人：展示 `轉帳建議`，如 `小美 → 阿明 HK$200`。
- 若未指定：显示说明 `尚未指定付款人，暫時只顯示各人分攤金額。`，入口 `補充付款人`，不得虚构转账。
- 主按钮 `分享結算`；次级 `儲存計算記錄`（Free 不限条手动历史）和 `加入活動`。
- `加入活動` 必须选择已有活动或新建活动；对成员映射、付款人、重复费用预览后才提交。
- 分享结果包含生成时间，避免一张很久以前的 PNG 看起来像实时余额。

### S05 — 活動列表

- 两个区：`進行中` 与 `已完成`；每个活动显示名称、日期、支出总额、结算状态。
- Free 已有进行中活动但仍可以查看全部已完成活动；点 `建立活動` 使用 M02。
- 允许对已完成活动查看历史、分享和补录还款；Pro 不改变原有记录的可读性。
- 搜索（如果 1.0 需要）只按活动名本地过滤，不提供虚假云端结果。

### S06 — 建立／編輯活動

- 必填：`活動名稱`、`幣種`、至少一个成员；建议 `至少兩位` 作为体验默认但单人历史记录并非数学错误。
- 可填日期；默认当天；成员复用最近名字但不自动合并重名。
- Free 创建时最后一步必须原子校验同时最多一个进行中活动，防止连续点两次出现第二个。
- 已有费用的活动币种不可直接更改；如未来要支持兑换，另立功能，不静默变换数字。
- 新建时不强制录入首笔消费。

### S07 — 活動詳情

- 顶部：活动名、状态 `進行中 / 已完成`、结算状态 `已結清 / 未結清`；两个状态独立。
- 摘要：原始支出、已登记的商家退款、有效总费用、参与者与净余额。
- 支出列表：金额、付款人、日期、模式、是否有退款。
- 进行中：主按钮 `新增支出`；下方 `查看結算`、`完成活動`。
- 已完成：主按钮 `查看結算`；允许 `記錄還款`；新增、修改费用、商家退款一律先进入 M04 重开流程。
- 对历史复杂 Pro 费用在权益不可用时仍允许查看计算明细，不删除/重算数据。

### S08 — 新增／編輯支出

- 字段：支出名称、日期、币种继承活动、实际账单总额、参与者、主分摊模式、付款人。
- 费用明细按需展开；Free 输入真实服务费、10% 快捷和固定优惠；Pro 可选高级分配策略。
- 同单 Pro 多付款人要求每人实付金额合计=原始商家账单额；Free 一位实际付款人付清该笔。
- 若已有成员间还款：编辑时先显示 M06 的旧/新差额和对余额影响；已发生还款原始记录保持不动。
- 单笔只可选一个主模式，不出现“逐项+多老板+比例”复合开关。
- 正式保存必须具备付款人；关闭前草稿可回退，提交不丢数据。
- 费用详情关联 M07 商家退款，**基本退款 Free 开放**。

### S09 — 活動結算

- `每人收支`：向商家实际垫付减商家退款、应承担额、已登记的成员间还款、当前净额。
- `轉帳建議`：展示确定性、便于操作的建议，不声称“数学最少笔”；每行可选择 `記錄還款`。
- 建议列表数据随费用修改、退款、还款自动重新计算；**建议绝不等于已确认付款**。
- `全部已結清` 仅在当前全员净余额为 0 时显示，与活动是否完成无关。
- 已完成且有欠款时显示两个并列状态 `已完成` 和 `未結清`，仍允许记录还款。

### S10 — 記錄還款 / 更正

- 预填转账建议的付款人、收款人、金额；支持输入部分还款、实际日期和可选备注。
- 确认文案明确：`此操作只會記錄轉帳，不會代你轉帳。`
- 不允许超出当前可结算余额的常规还款。连续点击提交必须幂等；相同姓名/金额但不同事件不应错误合并。
- 错误还款记录：`作廢紀錄` + 重新登记正确记录，保留原纪录可追溯。
- 已完成活动仍可直接操作，不强制重开、不占 Free 名额。

### S11 — 分享預覽

- Free 默认 `簡約清單` 模板：活动名/时间、币种、总额、每人份额、可选转账建议。
- 输出切换 `繁體中文 / English`；与 App UI 语言独立。
- Pro 模板建议 `Editorial Receipt`（编辑式收据）、`Compact Card`（紧凑群聊卡片）；支持 PDF、CSV。
- 不展示成员私人备注或付款凭证；可选不显示金额之外的活动细节；由用户决定是否分享。
- 超长姓名、多位成员、JPY/英文字串需要自动换行或长图排版；系统分享优先，相册保存时才申请对应权限。
- 页脚推荐 `根據輸入資料計算 · 轉帳需自行確認` / `Calculated from entered data · Transfers must be confirmed separately`。

### S12 — Lifetime Pro

- Hero：`解鎖更靈活的分帳方式`，副文案 `聚餐、旅行、多人墊付，一次買斷。`
- 以四组实用价值展示：① 同时管理多个活动；② 复杂费用（逐项菜品、份数/自定义比例、多位请客者）；③ 单笔多人垫付与高级服务费/优惠分配；④ 专业分享与导出。
- 对照区：Free 永久可快速 AA、一个进行中活动但费用不限、基础结算/退款/备份；不要暗示这些需要 Pro。
- CTA 使用 App Store 返回的**真实本地币种及价格**：如 `以 {storePrice} 解鎖 Pro`；不把 HK$28 测试价写死。
- 文案 `一次購買，解鎖本 App 的 Pro 功能`、`非訂閱`、`恢復購買`；购买权益以 Apple 的可验证交易为依据，不能由本地备份冒充。
- 商品加载：loading / available / failed / purchase pending / purchased / cancelled / restore success / restore none 都要有明确定义；失败时仍可继续 Free 使用。
- 审核环境：明确测试 iPhone 和可用的 iPad 环境，不能因为审核设备的商品价格加载失败而导致全 App 不能使用。

### S13 — 設定

- `一般`：语言系统/繁中/英文、默认币种（只影响新建项目）。
- `資料`：手动导出备份、从备份恢复、校验、覆盖前确认、恢复失败不破坏现有数据。
- `Pro`：当前权益、升级、恢复购买（已经 Pro 时显示已解锁）。
- `關於`：隐私政策、支持页面、版本、无需登录与离线说明。
- 系统语言变化不会自动覆盖手动选定的应用语言；分享输出语言独立。

## 6. 财务领域规范（实现前必须严格遵守）

### 6.1 定义与单位

| 领域名 | 含义 | 备注 |
|---|---|---|
| 原始账单 `gross` | 商家实际收取的总额 | 不因以后商家退款而覆盖原始支付事实 |
| 消费份额 `allocation` | 某成员最终对该费用应承担的金额 | 含请客承担、服务费、优惠等影响 |
| 向商家支付 `merchantPayment` | 谁实际付给商家多少 | 免费单人/Pro 同笔多人 |
| 商家退款 `merchantRefund` | 商家返还给哪名原付款人多少 | 是真实事件，不能装成原账单笔误 |
| 成员间还款 `settlement` | 谁实际转钱给谁 | 不等同“建议转账” |
| 建议转账 `suggestion` | 当前净余额推荐的下一笔转账 | **不是真实支付**、不可直接视作结清 |

单笔费用的约束：

```text
sum(merchantPayments) = gross
sum(merchantRefunds) <= gross
currentEffective = gross - sum(valid merchantRefunds)
sum(currentAllocations) = currentEffective
sum(netMerchantPaid) = currentEffective
```

整个活动中每个成员余额（以最小货币单位整数表示）：

```text
netBalance(member)
  = grossMerchantPaid(member) - merchantRefundReceived(member)
    - currentAllocations(member)
    + actualSettlementsSent(member) - actualSettlementsReceived(member)

sum(netBalance(all members)) = 0
```

**解释**：余额正数为该成员应收，余额负数为应付；只有全体余额为零才显示 `已結清`。完成活动、退款、费用更正、补录还款都不自动“付款”。

### 6.2 数字正确性

- 金额内部必须使用币种最小单位的**整数**；UI 字符串不得直接成为财务运算的权威来源。默认候选 HKD、CNY、MOP、TWD、USD、JPY；币种分位元数据在实现前核验，JPY 无小数。
- 选择**最大余数法 + 固定参与者快照顺序 + 稳定 ID**作为确定性分摊规则；对已保存历史保持原分摊及规则版本。例：HK$100 / 3 人 → 33.34、33.33、33.33。
- 百分比建议定点整数表示（最多 2 位百分比小数）；份数仅正整数；不能因为浮点误差/四舍五入导致合计不一致。
- 不接受负数输入作为正式账单。负向真实金额必须以**商家退款**或明确的优惠/费用调整字段记录。
- 费用项目、分摊金额和原始商家付款合计必须经过同一事务的守恒检验，不允许数据库里存在只有一半数据的正式支出。
- 整数溢出、过大金额、空输入、币种精度非法都必须阻止提交并给出明确提示。具体金额上限仍待最终确定。

### 6.3 四类主分摊模式

**A 平均分攤（Free）**：仅将本笔参与者均分有效总额；未参与者承担 0；人数 1 可计算但无“谁转给谁”。

**B 請客分攤（Free 单请客者；Pro 多请客者）**：
- 老板输入**最终承诺承担的固定金额或总额百分比**，不是“其自己 AA 份额之外再加的金额”。
- 优先固定老板承担额，再对剩余部分均分。默认余款由其他人分；用户可勾选老板也分余款。
- 如果固定额超过有效账单总额，拒绝提交；余款大于零时必须有余款分摊者。
- 示例 5 人、1000、老板承担 600：老板不参与余款 → 600/100/100/100/100；参与余款 → 680/80/80/80/80。
- Pro 多老板承诺总额不得超过当前有效账单额；也不可和逐项商品及自订按人比例混为单笔复合模式。

**C 各自消費（Free 各人总额 + 共享总额；Pro 按项目）**：
- Free 可写每人消费的合计与公共消费总金额，并选择公共消费参与人；按参与者均摊共享消费。
- 多个不同共享子群组的逐项费用属于 Pro，不让 Free 必须列出每道菜。
- Pro 每个项目支持名称、数量、**项目总金额**、分摊参与者；数量不是参与人数。
- 先以每人原消费作为基准，再施加允许的服务费和折扣分配规则；任何一项若无人参与，阻止确认。

**D 自訂分攤（Pro）**：
- 按个人固定金额、总额百分比或正整数份数，必须让分摊合计恰好等于有效账单总额。
- 比例总和须为 100%，不自动默默吸收差额；固定额合计不符必须修正。

### 6.4 实付总额、服务费、折扣

有两种输入视角：

1. **实付总额（默认）**：用户输入最终商家收取的数字，比如 1100 已包括 10% 服务费。算法只能分 1100。
2. **费用明细（展开）**：消费小计 S、固定优惠 D、实际服务费 F / 10% 快捷、可选明确调整 A、实付总额 T，必须满足 `T=S-D+F+A`。

由实付总额切到明细须确认原数是否包含服务费；不得直接把原总额当小计再次加费。

快捷 10% 服务费以**优惠前商品小计** `F=round(S×10%)` 为明细模式默认基数；可以主动切换优惠后 `F=round((S-D)×10%)`，以商家实际费用为最终核对依据。折扣和服务费默认按原消费份额比例分配且守恒；Pro 可指定更细规则。**直接输入最终实付金额时不得额外添加 10%**。

### 6.5 商家退款（1.0；Free 也必须能用）

- 在进行中活动的费用详情进入 `記錄商家退款`，输入金额（必须大于零）、发生日期及各成员承担额的减免明细。**退款接收者为实际收到退款的活动成员。默认原商家付款人，但允许选择其他合法活动成员。**
- 默认建议按原承担额比例减少，并允许将退款只分配给指定人，前提是减少金额总和恰好等于退款额、任何人的新承担额不得低于 0。
- 已登记的商家退款累计不能超过该费用原始收取金额；完全退款后原始费用和付款、退款历史仍存在，当前有效额可为 0。
- 退款必须留审计记录；要作废退款也应留痕，不能把真实退款变成“编辑原始账单”的备注。
- 已完成活动必须先重开，且 Free 检查同时只有一个进行中活动；已完成活动**仅成员间还款**可直接补录。
- 示例：A/B 原先各担 50、A 先付商家 100、B 已还 A 50，商家后退 20 给 A 且两人各减 10 → 最新 A 应向 B 还 10。

### 6.6 账单笔误更正、真实还款与转账推荐

- **笔误更正**：修改原始费用记录、实际付款金额与各人承担，预览新旧净余额，保留费用版本变更；**不自动改变已记录的成员间还款**。
- **成员间还款**：仅用户确认真实转账后记账；可以部分还款，含付款方、收款方、金额、实际日期。作废或更正应保留审计记录，不物理改写成另一个事实。
- 常规还款只允许当前付款方为债务人、收款方为债权人；金额不超过双方余额较小者。异常的“现实转错/超额转款”首版引导核对和纠正，不偷偷创建额外债务。
- 建议转账算法采用确定性的净额债务人→净额债权人匹配，按绝对金额降序且稳定 ID 破平；**只能说尽量减少转账，不得保证绝对最少笔数**。
- 每个记录使用稳定唯一 ID 和提交幂等性；连续点击不能产生两个相同实际事件；但真实发生两次同金额不同事件可各自登记。

## 7. 状态机与权限保护

### 7.1 活动状态 × 结算状态

| 活动状态 | 结算状态 | 合法组合 | 交互 |
|---|---|---|---|
| 進行中 | 未結清 | 是 | 增加/更正支出、退款、登记还款、完成 |
| 進行中 | 已結清 | 是 | 继续记账或选择完成 |
| 已完成 | 未結清 | 是 | 看历史、分享、**登记/更正还款**；费用和退款须先重开 |
| 已完成 | 已結清 | 是 | 看历史、分享；若真实还款记录被纠正，状态可能再次未结清 |

- Free 创建或重开活动时的**数据库最终提交**必须原子校验全库最多一个 `進行中`；不能只在 UI 层禁止按钮。
- Free 已有其他活动时，拒绝重开但保留当前已完成活动的查看/补记还款权利。
- Pro 数据恢复到 Free / 权益临时不可用：**不删除原数据**。历史可看、基础分享、备份；新的高级操作受权益限制。明确验证为 Free 且存量超出 1 个进行中活动时，可查看、结算、还款、完成和备份，但不得新建、重开或继续修改费用；待活动数减至 1 个及以下才恢复 Free 范围内的新费用编辑。unknown 不自动等同 Free，遵循最近可信的权益证据和安全校验策略。
- 已完成活动补录还款不调用 `reopen`，亦不占新活动名额。

### 7.2 草稿、编辑与事故防护

- 快速试算退出编辑自动保存最近 1 份草稿；手动保存历史不限条；已提交正式费用使用版本号与事务提交，不将输入半成品混入账本。
- 新建/转换的同一条快速试算只能成功入账一次，失败后可安全重试。
- 删除有财务历史的成员不允许直接级联删除；更名不会改变成员 ID、金额或余数顺序快照。
- 数据备份恢复必须**先校验再请求同意**；明确区分本机资料与 StoreKit 购买权益。建议 1.0 只做整库覆盖式恢复，不做无提示合并。

## 11. 本地数据模型（领域概念，非数据库迁移）

| 概念实体 | 必要含义 / 核心数据 | 约束 |
|---|---|---|
| AppSettings | 语言模式、默认币种、外观偏好 | 手动设置持久化 |
| LocalMember | 稳定 ID、显示昵称、创建时间 | 同名不同 ID、不合并 |
| Activity / ActivityMember | 活动状态、单币种、成员快照 | 完成/结清分离；Free active 配额在事务中验证 |
| Expense / ExpenseRevision | 标题、时间、总额、主分摊模式、版本及更正理由 | 更正留痕；一费用一主模式 |
| ExpenseBreakdown | 小计、服务费、优惠、差额确认 | 不能二次加费 |
| ExpenseAllocation | 成员 ID、当前承担金额、依据、舍入快照 | 合计等于当前有效金额 |
| MerchantPayment | 商家付款人和原始支付金额 | Free 1 位、Pro 可以多位 |
| MerchantRefund | 退款金额、原支付人/接收人、承担减少明细、时间、状态 | 退款事件可追溯 |
| Settlement | 成员间真实还款的方向、金额、时间、作废/更正 | 不可从建议自动确认 |
| QuickSplitDraft / QuickSplitHistory | 未正式入账草稿、可选保存记录 | 缺付款人允许试算，不可变正式费用 |
| Entitlement | 商店产品标识、可验证交易、缓存状态 | 备份不能伪造购买资格 |
| BackupManifest | 格式版本、各资产哈希/完整性信息 | 先校验，失败不替换现有数据库 |

**工程原则（未来交付实施阶段才启用）**：迁移只向前、事务性写入，金额引擎是无平台依赖的纯业务模块；数据重算、历史展示、分享图片必须从同一份权威账目衍生。正式技术栈候选 Expo + React Native + TypeScript + `expo-sqlite`，由未来架构阶段确认实际版本。禁止在这轮写 schema 或应用源码。

## 12. Pro 商品状态与定价约束

- 非消耗型单商品 Lifetime Pro，产品 ID/Bundle ID 未定；香港区价格讨论参考 HK$28 或 HK$38，不是最终价格。
- 展示的是商店返回的本币种价格，不直接硬编码数字；价格 loading/error/retry、取消、待处理、购买成功、恢复无结果均有 UI；无有效价格时不启用购买 CTA，但 Free 保持可操作。
- 保留购买之前的试算/活动编辑上下文，购买完返回原入口，不能把取消当作失败。
- 不在首次打开强制弹 Paywall，不在退款、备份、无限 Free 费用追加、基础 PNG 这些功能上收费。
- 历史 Pro 资料在无法验证有效权益时至少可查看、备份，不可被无声删除或降级计算。

## 13. 1.0 的明确非目标

- 注册登录、服务器/云同步、好友在线共同编辑、邀请链接实时协作。
- 银行/FPS/PayMe 自动付款、到账验证、自动发送催款信息。
- OCR 小票自动识别、AI 分账/抽取菜品、餐厅菜单服务、商家接入。
- 活动内混合币种和自动汇率换算；自动识别银行账单。
- 一笔费用同时叠加逐项分账 + 多老板 + 自定义比例的自由复合引擎。
- 商业监控或用户追踪服务（若以后加入，另做隐私决策）。

## 19. 五项已批准决策的详细实施规格与 T08 测试（F18–F22）

> 原 v0.8 的 DEC-P01–DEC-P05 已于 2026-11-05 被用户逐项批准，全部升级为已冻结条款；不再作为 Proposed。下面保留细节，避免短表格遗漏边界情况。

### DEC-P01 / O02：快速试算历史与草稿（已批准）

**冻结规则**：Free 允许不限次数计算与**不限条数的手动保存**；仅保留最近 1 份尚未提交的自动草稿。保存结果为计算快照，不是活动费用，也不占进行中活动名额。保存时保留币种、成员稳定 ID、模式、参数、计算结果、可选商家付款人、创建时间与算法/Schema 版本。没有指定付款人也能保存结果，仅不能产生实际转账建议。

- 试算不因用户退出立刻消失；下一次打开快速分账可继续当前草稿，明确 `放棄草稿` 可重新开始。
- 手动保存的历史不因为生成新的草稿而覆盖；用户可单条删除历史，删除需确认；导出与备份包含手动历史。
- `加入活動` 是显式、一次性转换，须填写正式付款人、选择目标活动及确认成员映射；同一历史结果不能重复生成同一笔正式费用，重复提交须幂等。
- **不实施**后台自动把每次按键都存成一个历史条目、自动无限增长历史。

**界面微文案**：`儲存計算結果` / `Save calculation`；`繼續上次草稿` / `Resume draft`；`這只是計算記錄，尚未加入活動帳本。` / `This is a saved calculation, not an activity expense.`

### DEC-P02 / O03：服务费、折扣与真实实付总额（已批准）

**冻结规则**：默认单个大输入框含义为「已含全部费用的最终实付金额」，**不会额外加上任何服务费或折扣**。只有用户主动切换到 `按明細計算`，才录入商品小计、固定折扣、服务费与实际最终应付金额。

1. `按明細計算` 默认：服务费百分比的基数为**折扣前商品小计**；清楚显示基数并允许切换至**折扣后商品小计**。
2. 10% 快捷项与「实际服务费金额」是互斥的金额来源，不可叠加；若使用百分比计算，必须把金额舍入到对应币种最小单位。
3. `最终账单 = 商品小计 − 固定折扣 + 服务费 + 明确的调整项（如有）`。折扣不可超过有效小计；实际收据总额不一致则提示差额并阻止正式入账，直到用户核对并主动修正。不能私自塞入舍入差额。
4. Free 的服务费和固定优惠按参与者原消费权重进行稳定、守恒的默认比例分配（余额为 0 的特殊情况另行明确处理）；Pro 可以按规则自定义分配。所有成员最终金额不可为负，固定余数顺序可重现。
5. 场景：小计 HK$900、折扣 HK$50、10% 服务费：优惠前计费=HK$940；优惠后计费=HK$935。直接输入 HK$940 最终总额则只分 HK$940。

**界面微文案**：`這是已包含服務費及折扣的最終帳單嗎？` / `Does this amount already include service charges and discounts?`；`按明細計算` / `Calculate from details`；`服務費按折扣前計算` / `Service charge before discount`；`服務費按折扣後計算` / `Service charge after discount`。

### DEC-P03 / O04：本地备份与恢复（已批准）

**冻结规则**：Free 可使用完整手动备份与恢复（SQLite 快照及相关本机资产），不需要 Pro；1.0 支持**验证后整库替换**，不做智能合并、云端同步，也不允许部分数据库无提示恢复。

- 备份含格式版本、数据版本、数据摘要/哈希、时间、相关媒体资产清单和校验值；SHA-256 用于完整性检查，不宣称能够抵御主动伪造。
- 导入先解压至临时目录，验证完整性、数据关系、金额守恒与版本兼容；必要迁移先在临时数据副本执行。
- 预览：`將恢復 {activities} 個活動、{expenses} 筆費用及 {repayments} 筆還款`；明确提醒会**取代目前本機資料**；用户确认后一次原子切换；失败自动保留原库。
- 恢复成功与失败都需给出明确结果；同一份备份恢复两次不造成双重账目。未来版本备份不能由旧版本擅自强行导入。
- StoreKit/Apple 的 Pro 购买资格不由备份文件赋予；恢复后以可信商店交易状态决定当前高级编辑权限，**绝不能为了无 Pro 就删掉历史高级数据**。

**界面微文案**：`恢復備份會取代此裝置現有的分帳資料。這個操作無法自動合併兩份資料。` / `Restoring will replace the split data on this device. The two datasets won't be merged.`；`驗證失敗，沒有變更原有資料。` / `Validation failed. Your existing data was not changed.`

### DEC-P04 / O10：Pro 权益暂不可确认 / 已确认无 Pro，且历史超免费配额（已批准）

区分 **可信 verified Pro**、**明确 verified Free/已撤销** 和 **暂时无法验证 unknown**，不得将网络断开直接当作 Pro 已丢失。已验证的非消耗型历史交易应按 StoreKit 的有效性与撤销信息核验；缓存只能按可靠性策略用于暂时离线可用性，不能把用户伪造的本地标记视作购买证明。

当已**明确**不是 Pro 且数据中已经有 2 个及以上进行中活动：
- 完整保留数据、余额、全部历史和备份权利；能查看、执行分账结算、记录/更正/作废真实还款、完成活动。
- 不允许再新建进行中活动、重开已完成活动、继续使用 Pro 专属编辑入口；不将旧 Pro 分摊改写为普通均分。
- 历史的已记录真实费用不删除；对“超额进行中活动能否追加基础费用”，为避免含混，**明确按只读账务费用处理**，待数量减少到 ≤1 且确认为 Free，才按 Free 权限继续编辑基础支出。
- unknown 时展示 `正在確認購買狀態`，不擅自破坏历史；允许历史查看、备份、还款和结算。商店验证恢复后按新结果刷新高级入口。

**界面微文案**：`目前無法確認 Pro 狀態。你仍可查看活動及記錄還款。` / `Pro status can't be verified right now. You can still view activities and record repayments.`；`你的活動資料已完整保留。` / `Your activity data is preserved.`

### DEC-P05 / O12：有商家退款时更正原费用（已批准）

**冻结规则**：将「事实发生」与「更正录入错误」分开；原费用和退款均保留事件追溯，不允许修改费用时顺便删掉已有退款。

- 进入更正流程先计算旧版/新版原始商家支付、已收到真实退款、退款后的净费用、参与者承担额、当前欠款与还款建议，并在确认前显示差异。
- 新商家原始实付金额必须 ≥ 已登记的**有效**累计退款；否则拒绝单纯更改原费用，需先明确登记退款记录更正/撤销（保留更正轨迹），并在同一审核流程中完成一致性校验。
- 如果仅修改消费分配而不改变退款金额，用户必须显式复核退款减少哪些成员承担额；不可自动重新分配退款责任。
- 不允许单一成员最终承担额变为负数；不能更改已经发生的成员间还款事实。结算出现反向转账建议是合法结果。
- 如用户误录商家退款，不物理删除原事件，以作废/更正关联事件留审计痕迹；在一个事务内完成所有关联修改，失败不提交部分变化。
