## 2. 编辑现有正式费用

- 根据**当前费用有效版本**预填，复用 S08 已有控件、`SplitModeSelector` 和分账引擎；不要复制第二套分账方式及舍入规则。
- 允许在现有合同/权益范围内编辑：费用名称、金额、日期、当前支持的分摊模式与参与成员、分摊参数、商家实际付款人，以及适用的明细字段。复杂历史 Pro 数据保留，只读与写入权限应分别判断。
- 原费用稳定 ID、历史修订、实际还款/退款事件 ID 不能改写；编辑不等于新建第二笔费用。
- 币种继承活动，不支持隐式换币；正式费用必须有实际商家付款人（Free 单笔一人付清、Pro 规则按既有权益）；付款人可不参与本笔分摊，只要合法属于活动。
- 金额使用货币最小单位整数和现有精确分摊/尾差规则；拒绝非法精度、非正金额（以既有合法合同为准）、空名称/错误成员/重复映射及不守恒方案；详细错误显示在相关字段附近。
- UI 底部操作「預覽更正影響」，不直接保存更正。关闭、返回或确认取消不修改数据库。保留正在编辑的数据。

## 3. 提交前的「更正影響預覽」— 核心安全门

预览必须从现有 **finance revision / correction service** 推导，并在同一可复现账本上下文中计算，绝不根据 UI 自己拼金额。

预览至少清楚展示：

1. **本笔费用：** 旧版 → 新版（费用名称、商家原始付款/付款人、gross、有效退款、净费用与分摊方式/参与者的实际变化）。
2. **每位相关成员：** 原应承担额 → 新应承担额，含保持不变及新参与的成员；校验分摊合计与净额守恒。
3. **整个活动：** 有效费用总额、所有成员旧/新净余额、尚待结算总额、转账建议旧/新方向（若发生变化）。不要只显示该笔费用的局部差额，因为旧成员还款可能导致反向建议。
4. **真实历史：** 活动中已有成员还款的事实保留不动（即使因此出现反向结算）；已存在的有效商家退款不可被静默调整、删除或自动改分配。
5. **风险与限制：** 有真实商家退款时显式展示累计退款、原付款人退款接受者及各成员退款承担减少分配。修订新 gross 不得低于仍有效的累计退款；若现有退款分配与新版承担不相容/任一净承担为负，必须禁止提交并解释如何先核对或作废错误退款（后者 UI 留下一阶段）。

**过期预览保护**：从预览到确认前如该费用版本、关联有效退款/作废、成员还款/作废、活动状态或其他影响全活动结算的事件发生变化，禁止以旧预览提交，提示重新预览。真正写入事务内必须重新校验最新状态，不仅依赖前端的判断。若底层已有 revision guard/token/version，直接复用，不另造不安全的缓存锁。

确认页底部「返回修改 / 確認更正」。用户确认前零写入；二次提交或重试使用现有稳定的修订请求 ID 和幂等机制，不能生成两个相同更正版本。

## 4. 费用版本历史

- 费用详情可进入「修訂歷史」，列出 v1 原始版和后续有效历史修订，按现有排序展示时间、主要变更摘要、金额/分摊前后，当前版本突出显示。
- 审计历史为**只读**；不能覆盖或物理删除原始费用、旧 revision、已登记退款/还款。
- 若底层只支持已存储的某些历史字段，优先真实呈现并在交付中说明限制；不得根据新值猜造旧值。
- 若本阶段无法保证完整历史业务字段展现，应明示而非伪造；允许由 Codex 审计底层后提出最小安全变更，但不要轻率引入 Migration。

## 5. 验算示例（非硬编码；当前用户模拟器账本有历史变动时以真实数据为准）

「旅行」活动：4 位成员 a、b、Chris、d；现有两笔正式费用：「吃饭」560 和「晚餐」560，均由 a 向商家付款；「晚餐」原由 a、b 各承担 280，其它两人承担 0。**该示例假设当前没有有效成员还款或商家退款**（之前作废的还款历史仍保留，不计入有效余额）。

更正「晚餐」为四人均分、总金额仍为 HKD 560、付款人仍为 a：

| 成员 | 该笔费用旧承担 | 该笔费用新承担 | 整个活动更正前净额 | 更正后净额 |
|---|---:|---:|---:|---:|
| a | 280 | 140 | +560 | +700 |
| b | 280 | 140 | −560 | −420 |
| Chris | 0 | 140 | 0 | −140 |
| d | 0 | 140 | 0 | −140 |

- 本笔 gross：560 → 560；活动有效总费用：**1,120 → 1,120**，不因重新分摊而变化。
- 付款给商家的原始事件不变；全员净额合计恒为 0。
- 旧/新转账建议须由现有引擎计算，不能硬编码方向或笔数。
- 如果测试库已经存在其他**有效**还款、退款或不同费用分配，以上成员净额示例**不再直接适用**；应根据 SQLite 的真实账本呈现。

## 6. 技术约束和错误处理

- 使用原有 SQLite 串行写队列 + 原子事务。校验、预览一致性检查与正式写入的正确性由服务/Repository 保证，UI 不能绕过。
- 修订只增加新版本并更新现行投影，仍保留原始审计历史。不能修改 `member_transfers`、`merchant_refunds`、`financial_voids` 的已有事实记录。
- 不重新实现财务余额、分摊尾差、转账建议、服务费/折扣算法。
- 必须处理费用/活动不存在、活动已完成、Free 名额/Pro 许可限制、过期预览、退款冲突、写事务回滚和多次提交。
- iPhone 安全区、列表滚动与键盘避让；返回时保持原编辑状态；长成员列表不被固定底部按钮遮挡。
- 繁体中文用语与已验收 S01–S10 保持一致；英文既有本地化结构能适配则复用，不引入第二套硬编码文案。
- V3.2 配色：底 `#FDFCFB`、卡片 `#FFFFFF`、主字/按钮 `#282828`、边框 `#E7E5E2`，浅中性灰辅助；不引入大面积奶茶色、彩色渐变或不必要图标。
