## 1. 本階段唯一主目標

**把 S09 的轉帳建議接到真實「已發生的成員間還款」登記流程**，經用戶明確確認後原子寫入 SQLite，返回 S09 更新淨額與建議。

- 支援全額或**部分**還款、實際日期、可選備註。
- **只記錄使用者確認已經發生的轉帳，不替使用者轉錢。** 不與支付 API/FPS/PayMe 串接。
- 保留每筆還款獨立事件；錯誤事件的「作廢舊事件／重登正確還款」UI **下一小階段**實作，不要在本輪擴大範圍。
- 目前既有領域和 Repository 已有成員還款事件及核驗，**必須復用**，勿重寫帳務演算法。

## 2. 導航、入口及 S09 連接

- S09 `轉帳建議` 下方現有「記錄還款（下一階段）」占位替換成真實入口。
- 點選某條建議 `b → a / HKD 560` 時，可直接開 S10 並預填該付款人、收款人和**當下建議金額**。若設計仍採共用底部按鈕，至少讓使用者能選中該條建議後進入表單；不可假定永久只有一筆建議。
- S10 可從 S09 進入並返回 S09 對應活動與原有分段（優先保持 `轉帳建議`）；成功後重新載入最新一份一致性 SQLite 快照。進入 S10 時也應取得真正活動及成員資料，不以畫面上舊資料為唯一依據。
- **已完成但尚未結清**的活動同樣能直接登記還款，**不要求重新開啟，不占用 Free 進行中名額**。
- 0 財務事件、已結清或目前不存在合法轉帳方向時，不應給出可成功提交的假入口；顯示合適空態。
- 頂部只有左返回箭頭、居中「記錄還款」，**不要在右側再放重複的「返回」**。

## 3. S10 表單（高保真第 2 屏）

- **付款人（必填）**：活動內實際支付還款的成員；預填所選轉帳建議的付款人。
- **收款人（必填）**：活動內實際收到還款的成員；預填建議收款人。不得等於付款人。
- **還款金額（必填）**：預填當下建議金額，但允許改成正數的部分金額；幣種鎖定活動幣種，採既有最小貨幣單位與格式化/解析邏輯，JPY 等零小數必須正確。
- **轉帳日期（必填）**：默認使用裝置**當天本地日期**，可編輯實際發生日期；輸入與保存不可因時區解析導致隔日。遵從現有按事件時間排序及時間線合法性限制；過去/未來日期若不符合既有賬務事件順序要求，明確報錯，**不要悄悄改成現在時間**。
- **備註（選填）**：例「FPS」、「現金」，無須取得外部支付證明。檢查現有 schema/API 是否可完整保存及重讀；若缺少備註欄位，使用**向前安全 Migration** 增加可空備註欄位與兼容倉儲讀寫；不得只把備註放在本地 UI 假裝已保存，不得破壞舊記錄、備份或 Migration v1–v7。若資料型別或欄位已存在則不要新增 Migration。
- 支援鍵盤避讓、表單捲動、狹窄螢幕、安全區；輸入錯誤直接在字段附近提示，保存失敗不清空輸入。

## 4. 再確認（高保真第 3 屏）

提交前先以清晰的確認 Sheet/Modal 顯示：付款人、收款人、幣種及**實際還款金額**、日期、備註（有才顯示）。

必須包含準確警語：**「此操作只會記錄轉帳，不會代你轉帳。」**

- 用戶取消：不寫 SQLite、不改 S09。
- 用戶確認：才開始正式記錄；期間顯示進行狀態、防連點。
- 成功後可以展示「還款已記錄」成功狀態並返回 S09；絕不能使用「轉帳成功」等暗示 App 轉錢的字眼。
- 若提交競態期間帳務已變，必須以寫交易中**最新账本**重新檢查，提示重新確認，不能硬塞原先建議金額。

## 5. 帳務與交易安全（最高優先級）

1. 優先復用 `recordMemberTransfer` / 既有 Finance Repository，使用同一 SQLite 串行寫交易重檢活動、成員、幣種及現行可結算額。
2. 轉出額必須 `> 0`，不能超過**當下付款人的未付額和收款人的未收額**。不可根據 S09 開頁時的快照直接相信餘額。
3. 非法成員、同一成員付給自己、非法日期/金額/ID、已結清再提交，都必須返回結構化錯誤並且**零寫入**。
4. 使用**穩定事件 ID**處理同一次提交的雙擊/失敗重試/網絡似的 UI 重發（即使 Local-First 也要）。同一請求不得重複入帳；兩次現實中確實不同的還款即便付款人、金額、日期相同，也應有不同事件 ID，不可按金額/姓名去重。
5. 整筆操作失敗可重試，不能留下半個事件；成功後真正生成歷史 `member_transfers` 事件，所有既有費用、退款、分攤原始記錄不動。
6. 已完成活動**允許**真實還款；不得自動重開活動，也不得把「已完成」直接改成「已結清」。
7. 真實還款只改變**各成員淨額/建議**，不改變**活動有效費用總額、費用筆數**。
8. 會員間還款、商家退款是不同類型事件；**絕不**把這次還款記成商家退款。
9. 若需增加備註持久化，確保後續完整備份 / 恢復 schema 校驗與舊版本升級兼容性；僅做必要的向前變更和針對性測試，不擴大成備份重構。

## 6. S09 更新與數字驗收

此前「旅行」示例（如設備存在該資料）：正式費用 2 筆、總額 HKD 1,120；a 實際墊付 1,120，a/b 各承擔 560；Chris、d 初始淨額 0。

登記 **b 實際付給 a HKD 200.00** 後，必須顯示：

| 項目 | 登記前 | 登記後 |
|---|---:|---:|
| 活動有效費用 | HKD 1,120.00 | **HKD 1,120.00** |
| a 當前應收 | HKD 560.00 | **HKD 360.00** |
| b 當前應付 | HKD 560.00 | **HKD 360.00** |
| 有效已登記還款 | HKD 0.00 | **HKD 200.00** |
| 尚待結算 / 新建議 | b → a HKD 560.00 | **b → a HKD 360.00** |

再以**新的真實還款事件**記錄餘下 HKD 360.00 後，若全員淨額均為 0，S09 顯示「款項已全部結清」、轉帳建議空；活動即使保持 `進行中`，也可已結清。

示例是驗收資料，禁止硬編碼。多付款人、多收款人、部分還款、非 HKD 貨幣和已完成活動仍要動態計算。
