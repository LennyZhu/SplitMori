## 1. 目标与范围

实现 **S09 → 還款記錄列表 → 還款詳情 → 作廢二次確認 → 返回並重新計算 S09** 的完整可用链路。

- 查看全部已经真实登记的**成员间还款事件**，包括仍生效与已经作废的历史记录。
- 安全作废一笔**有效**的错误还款：**追加作废事件，而不是删除或覆盖原纪录**；之后 S09 应付、应收、转账建议实时变化。
- 已完成的活动可以查看及作废成员间还款，**无需重新开启、不消耗 Free 进行中活动名额**。
- **不实现**直接修改已入账金额/日期/备注、批量作废、退款管理、费用更正、实际银行转账、IAP/Pro。若用户需要更正还款，流程是「作廢旧纪录 → 使用 S10 重新登记正确还款」。本阶段不新增「编辑备注」等未获批准的功能。

## 2. 入口与导航（无转账建议也要可进入）

1. 在 S09「轉帳建議」与/或 S09 合理位置提供可见的 `查看還款記錄` 入口，带基于真实历史的数量。**即使全员已结清、转账建议 0 笔，也必须能进入还款历史。** 0 笔显示清晰空态，不能隐去访问路径。
2. 列表页与详情页沿用已有导航与安全区：只在左上角保留返回箭头，标题居中；不要右上角再放重复的「返回」。
3. 从历史页进入单条详情，再进入确认作废；取消返回详情而不写账；作废成功则刷新列表、详情状态和 S09。返回已有 S09 时，保持原活动上下文与尽可能相同的分页（优先「轉帳建議」）。
4. 提供加载、无记录、读失败重试及操作失败可恢复状态；不因为短暂切换页面重复触发写入。页面内容不得使用假记录。

## 3. 還款記錄列表（V3.2 白底极简）

- 来自同一个活动的真实 `member_transfers` 历史，按实际事件排序稳定展示（可用登记/发生时间，时间相同按数据库事件序号稳定定序；不要只靠 JS 不稳定排序）。
- 每项显示**付款人 → 收款人、金额和活动币种、真实转账日期、备注（有则显示）、有效/已作废状态**。
- 顶部可显示「有效已登记还款总额」和「历史记录条数」，**切勿把已作废金额计入有效还款**；已作废记录仍占历史条数。
- 点击任何记录都能查看详情；已作废记录仍可查看，但不再展示可执行作废操作。
- 只读取当前活动的还款事件，不把商家退款、费用、计算建议混入历史列表。

## 4. 還款詳情

- 展示原始真实还款事件：付款人、收款人、金额、活动币种、发生日期、可选备注、记录状态。
- 对有效还款提供 `作廢此筆還款` 危险操作入口。不要使用含糊的「删除」；也不要允许用户在这个页面直接修改历史金额。
- 对已作废还款显示 `已作廢`，尽可能展示对应作废记录的时间与原因（若既有 Schema/API 已支持）；保留原始金额与备注，禁用重复作废。
- 如果读取时还有效但确认时已经被其他请求作废，提示当前已作废并刷新，不生成第二条作废事件。

## 5. 作廢确认（必须明确且不会误导）

- 使用 V3.2 中性色 Sheet/Modal，显示付款人、收款人、原始金额、真实转账日期、备注（有才显示）。
- 文案明确：**「作廢只會更正 SplitMori 帳本，不會撤回或退回現實中的轉帳。」** 说明作废后该笔还款不再参与结算，历史仍保留。
- 可以提供简短的「作廢原因（選填）」仅在现有 `financial_voids` 本来支持时复用；不为此新增复杂 schema。
- 取消或关闭确认：**零写入**，不影响当前待结算金额。
- 必须确认按钮才能执行。提交中禁用重复点击，失败时显示结构化错误并允许重试，保留用户上下文。

## 6. 财务数据与安全（最高优先级）

1. 优先调用现有 `voidMemberTransfer`，沿用已有 `financial_voids`、财务事件队列和 SQLite 原子事务；不要独立重算财务余额，不新增重复作废表。
2. 对作废命令使用稳定作废事件 ID：同一请求重试返回原结果；同一原还款**最多一次有效作废**；不同 ID 针对已作废还款要返回明确冲突而非重复抵销。
3. 事务内部再次校验：目标成员间还款事件存在、确属该活动、事件类型是成员还款、尚未作废、日期与事件顺序合法，及现有账务安全约束。不得只信任前端列表快照。
4. **不得**物理删除、更改原 `member_transfers` 金额、日期、付款人、收款人、备注，不得修改任何原始费用、商家付款、商家退款、历史修订事件。
5. 作废只能影响**有效成员间还款合计、成员净余额、当前待结算及转账建议**，**不改变活动有效费用、费用笔数**。
6. 发生并发写入、失败或重试时不产生部分状态；失败后原账务不变，重新获取一致性 ledger 快照。已有历史还款不会因为作废较早的某笔而被悄悄删除。
7. 即使 S09 原本显示 `款項已全部結清`，仍允许从历史页面作废有效成员还款（前提是现有核心财务约束允许），从而重新出现真实应收应付；**与活动“进行中/已完成”状态无关**。
8. 保持旧数据库 Migration v1–v8 兼容；优先复用现有 v6 `financial_voids`，**无必要不增加 Migration**。读写新字段时检查备份/恢复与历史 schema 一致性，不做重构。

## 7. 核对案例（以现有「旅行」测试账本为例）

该活动 2 笔正式费用，合计 HKD 1,120，a 实际垫付 HKD 1,120，a/b 各承担 HKD 560，Chris、d 无承担金额。存在两笔有效**真实成员还款**：
- 第一笔：`b → a`，HKD 200（备注“第一次还款”）
- 第二笔：`b → a`，HKD 360

**作废第一笔 HKD 200** 前后应为：

| 财务指标 | 作废前 | 作废后 |
|---|---:|---:|
| 活动有效费用 | HKD 1,120.00 | HKD 1,120.00 |
| 原已登记历史事件 | 2 笔 | 保留 2 笔（第一笔显示已作废） |
| 有效已登记成员还款 | HKD 560.00 | HKD 360.00 |
| a 当前应收 | HKD 0.00 | HKD 200.00 |
| b 当前应付 | HKD 0.00 | HKD 200.00 |
| Chris、d 净额 | HKD 0.00 | HKD 0.00 |
| 当前待结算 | HKD 0.00 | HKD 200.00 |
| 转账建议 | 无 | **b → a HKD 200.00** |

注意：如果用户模拟器账本其实只有 HKD 200 一笔，还未登记 HKD 360，实际数字要按**真实账本**推导，不能强行匹配表格。可在自动化测试中创建独立测试账本核对上例。
