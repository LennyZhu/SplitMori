## A. S07 → 管理成员 → 新增成员

1. 在 S07「活動詳情」的成员区增加一个不喧宾夺主、可实际点击的「管理」入口，打开独立「管理成員」页面；返回 S07 后读取最新真实数据。已完成活动可只读查看，不能以未复开状态添加成员。
2. 「管理成員」显示当前活动、成员总数、成员真实显示名称和稳定 ID 绑定的列表；有正式财务记录的成员标明不可删除；新增入口位于列表下方。遵循已批准的两屏布局、统一导航、固定底部按钮和安全区。
3. 「新增成員」允许一次输入多个成员姓名（示例 c、d），支持增减输入行、空白与长度校验、键盘避让、提交防连点；预览当前人数/本次新增/预计总人数。禁止把 UI 示例姓名硬编码成默认业务数据。
4. 名称重复不代表同一成员：按既有 PRD 允许同名成员；每条成员具有独立稳定 ID。新增必须在一个受控 SQLite 写事务中完成，若任一输入无效或写入失败，则整批不落库；重复提交/重试不得重复插入同一批成员。优先复用现有 `addMember` 能力，在不破坏兼容性前提下新增必要批量接口/事务封装。
5. 允许在「管理成員」安全修改成员显示名称，但**不得改变成员 ID、活动归属或历史账务事件**；先核查 `members`/`activity_members` 关系，避免影响其他活动的同名/共享数据。涉及已发生费用的成员，历史分摊、付款、退款、还款快照及数额必须保持不变；如果现有数据模型无法安全按活动修改名称，先说明阻碍并采用安全的最小兼容实现，不做破坏性重构。
6. 本阶段**不提供财务历史成员的硬删除或自动合并**。如果非财务成员的删除需要额外审计，可暂不开放删除；不要把「编辑」伪装成删除。已完成活动不可改写历史成员归属。
7. 成功新增 c、d 后，活动人数从 2 → 4；旧两笔费用金额、原付款事实、a/b 净余额完全不变，c/d 初始余额为 0。S07 和 S05 回到前景/导航返回可及时刷新；快速历史转换流程重新进入时应读取新增成员，使 4 人的原快速历史可以分别映射到 a/b/c/d（仍以币种、活动状态和转换服务的验证为准）。**不要为了允许转换而改变既有历史分摊金额、尾差或一对一映射规则。**
8. 新增中的重入、返回、失败恢复、活动已完成时的竞争状态必须安全；不要仅用前端按钮保护事务有效性。
