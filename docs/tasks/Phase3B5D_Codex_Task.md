## 本阶段边界
只完成：**一条已保存的快速历史 → 已存在的、进行中且同币种的活动**。
原先未保存的临时草稿直接转换、新建活动并继续转换、Pro 多活动权限、完整活动结算等留给后续阶段，不能伪造成功。未保存结果的“加入活動”应明确告知先手动保存，或引导至保存操作；不得默默写入历史。

## 必须实现
1. 在目前真实可达的快速记录/结果入口提供「加入活動」操作。确保从已保存历史能进入，不建立孤立页面。如果记录详情仍是占位，做最小可用的记录详情入口即可，不额外扩张整套历史 UI。
2. 第一屏：显示来源快照摘要（币种、金额、模式、人数），只允许选择同币种且进行中的真实活动；已完成/不同币种不得提交。无可加入活动时显示准确空态及下一步说明，不提供虚假成功操作。加载、错误、返回和取消状态清晰。
3. 第二屏：填写正式费用名称（必填）；把来源每个稳定成员 ID 映射到目标活动的稳定成员 ID，禁止未知成员、遗漏和重复目标映射（本阶段采用一对一映射）；显式选定实际商家付款人（必须属于活动，可以不是消费承担者）；显示原分摊金额及映射后金额，并校验总额守恒、币种一致及份额尾差归属不变。若已保存原付款人且能映射，可预填，但用户必须能核对。
4. 正式创建沿用 `createQuickSplitConversionService(db).convertQuickHistory(...)`、Finance Repository 与事务/回执机制。不要自己重算原份额，也不要重新写整套账务。检查如何把费用名称经现有 Migration v7 `expenses.name` 随该次正式费用在同一事务持久化；旧接口行为须兼容，不能创建后再以不安全的第二次写入补名称。
5. 重复点击只触发同一个稳定转换请求；同一来源历史只可成功入账一次，重复请求返回既有回执，冲突显示清楚。失败时不得留下费用/付款/映射的部分数据。
6. 事务提交前重查活动状态、币种、所有成员有效性、商家付款人与来源历史；不能只依据界面之前读到的活动快照。
7. 成功后进入 S07 并强制刷新，看到真实新增的名称、付款人、费用数量、有效金额和结算状态。原快速历史保留但呈现“已加入活動”提示，不能再转入第二笔。
8. 失败、取消、导航返回后来源历史与原账务保持不变。中途切换目标活动，清理旧成员映射与付款人选项，不错误沿用。
9. 视觉与现有 S01–S08 共用 V3.2 颜色、字体/卡片；不要把 S08 “新增费用”模式选择器复制到本转换页，也不修改已通过的页面。
