# SplitMori｜技术架构决策 v1.0（ADR-001–007）

> 日期：2026-11-05。当前状态：**开发前技术方案已确认**；以仓库现有 `docs/PRD_v1.0_Master.md` 和 `docs/Decisions_v1.0.md` 为业务权威文件。本文件只确认工程边界，不改动 F01–F22。用户已将 v0.9 架构文档放入 `docs/architecture/`。**本文件的生成不是实际代码开发。**

## 一、已采用的架构

| ADR | 决策 | 实际做法 |
| --- | --- | --- |
| ADR-001 | 纯 TypeScript 领域计算层 | 核心金额、分摊、净额与建议转账不依赖 React Native、数据库、界面、IAP。 |
| ADR-002 | 当前费用快照 + 历史修订 + 财务事件 | 费用更正有修订版本；商家退款与成员间还款独立留痕，不引入完整 Event Sourcing 平台。 |
| ADR-003 | SQLite 单一事实来源 | Phase 2 实现本地单账本；集中串行写入、数据库事务及完整性保护。 |
| ADR-004 | 分阶段开发 | Phase 1 纯 TS 引擎，Phase 2 数据层，Phase 3 再接 App 界面；不提前接入 IAP。 |
| ADR-005 | Git 分支策略 | `main` 保持稳定；`develop` 集成；每个工作阶段使用 `feature/*`。不直接在 `main` 开发或自动合并。 |
| ADR-006 | 金额最小单位整数与精确比例 | 公开输入/输出使用安全整数最小货币单位；比例中间运算用精确整数/有理数；稳定最大余数法分摊。 |
| ADR-007 | 一致性备份与可恢复替换 | Phase 5 实施一致快照、校验、用户确认、暂存/原子切换与失败回滚；备份文件不能冒充 Pro 购买证据。 |

### 暂定技术计算约定

- 输入金额不得超过 JavaScript 安全整数范围；累加结果与计算中间值也要校验，非法/溢出立即返回错误。**单笔/活动更小的产品上限仍是工程待定常量**，不能伪称已获产品批准。
- 普通金额分摊按稳定最大余数法；服务费率计算恰好为半个最小货币单位时，**采用 half-up 作为当前实现默认**，与人员间余数分配严格区分。若最终计费与真实收据不一致，必须让用户输入实际服务费或修正账目。
- 一笔费用只允许一个主分摊模式。快速计算没有商家付款人可以出份额结果；正式入账必须有匹配实际总额的商家付款记录。
- 强调“Pro 权益 unknown”≠“确认 Free”，不得将不明状态当作退订或购买证据；这部分到 Phase 6 才接入商店能力。

## 二、开发节奏调整（产品负责人新要求）

**以完成功能为主，按功能增加少量直接相关的测试。不要先建设庞大的测试框架，也不要要求开发第一天就覆盖 PRD 的 98 项测试清单。**

- 先实现一个可用的薄功能切片，再做该切片的必要验证；每轮发现 bug 就补对应回归测试。
- Phase 1A 先交付金额/平均分摊/单老板请客；Phase 1B 再完成其余分摊规则；Phase 1C 再完成垫付、退款、还款、余额及结算建议。
- 每轮仅需 `typecheck`、可用的轻量单测、`git diff --check`；已有 lint 则运行。避免新增沉重工具链、性能/压力/随机属性测试，除非出现具体 bug。
- 金额守恒、余数与防溢出属于高风险底线，需要最少量但真实可执行的测试；数据库事务与商店支付等测试，等对应功能开发时再做。
- 不要求 Codex 跑 iOS 模拟器或真机交互；用户后续自行手动验收。
- 发行前仍须完成 PRD 规定的关键 P0 验收，但不前置于尚未开发的功能。

## 三、阶段边界与变更控制

- 第一阶段只做可独立运行的 TypeScript 计算代码和必要的最小工程配置。保留并遵守当前 `docs/`；禁止创建 Supabase、业务后端、EAS 证书、StoreKit 商品。
- 当前文件不会自行初始化仓库、安装依赖、执行代码或修改远程。用户明确将 Phase 1A 任务发送给 Codex，才代表开始该子阶段的实现。
- 如果实现中发现与 F01–F22 冻结规则冲突，不要自行修改 PRD；记录问题，等待决策。
