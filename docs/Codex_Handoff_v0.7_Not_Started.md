# SplitMori｜Codex 开发交接规划（v0.7，尚未授权执行）

> **仅供未来交接设计**。当前绝不开始编码、初始化 Expo、配置商店商品或部署。

## 0. 项目与协作基线

- 正式项目名：SplitMori；本地文件夹与同名 GitHub 远程仓库由产品负责人自行建立、关联。
- 先提交主 PRD 和决策登记；Git 仓库的第一阶段建议是**仅文档基线**，不混入任何正式应用源码。
- 未来架构候选：React Native + Expo + TypeScript + SQLite，离线/本地优先；iOS 首发、繁中/英文。
- 分支建议（尚未执行）：`main` 为稳定发布线，`develop` 为集成线，功能分支短期合并；每阶段完成 typecheck、lint、目标测试和 diff 检查。
- **CodeX 验证策略**：Codex 负责实现及轻量静态/单元测试；不指示其耗时地操作 iOS Simulator 或进行真实设备交互；真机/模拟器由用户本人手动测试并记录结果。

## 2. 每次 Codex 任务单的固定格式（将来才使用）

- 阶段目标、限定目录/文件、严格非目标与禁止触碰范围。
- 该阶段必须通过的 `Mxx/UXxx/Axx` 测试列表及输入期望。
- 允许修改的数据库迁移边界，是否涉及生产环境，后向兼容要求。
- 基本验证：typecheck、lint、纯函数单元测试、相关针对性自动化测试、`git diff --check`。
- 输出：修改文件清单、测试通过/失败、已知问题、需要用户手动模拟器/真机验收的清单。
- 任何可能调整财务公式、Free/Pro 边界、修改历史账目、写生产数据的方案必须先暂停实施并报备。
- 不上传账户密钥、Apple 证书、个人身份信息、.env 和已签名配置到 GitHub。

## 3. 一开始**不要**做的事

- 不复制 OrderMori 的 Bundle ID、App Store Connect 商品 ID、iOS 签名私钥或 EAS 项目 ID。
- 不因为想节省交互而把请客责任和实际商家付款放在同一列。
- 不在未接入商店之前硬编码港币价格假装商店返回值。
- 不把测试环境或正式后端部署为已完成（SplitMori 1.0 默认无后端）。
- 不自动重算覆盖历史退款/还款事件；不要让“完成活动”等于“全部付清”。
- 不开展完整 UI 大改之前就让复杂账务引擎进入正式活动数据表。
